# Development Plan

Phased per the master spec. Each phase: inspect -> plan -> implement backend -> migrations -> API -> Flutter UI -> tests -> docs.

- **Phase 0 — Discovery**: done (empty repo).
- **Phase 1 — Architecture**: done (this doc + architecture.md + database.md + api.md).
- **Phase 2 — Foundation**: Docker Compose (postgres, redis, backend, flutter web), backend bootstrap (NestJS, config, health checks, error handling, logging), auth (JWT + refresh), organizations, users, roles/permissions, migrations, seed data, Flutter app skeleton (routing, theme, responsive shell, API client, auth flow, login screen, dashboard placeholder).
- **Phase 3 — Inventory Core**: products, categories, brands, units (+ conversions), warehouses, locations, product variants, batches (FEFO-ordered), serial numbers (with traceability), the stock ledger + stock balance engine (opening stock, adjustments, transfers — all row-locked and transactional). Not yet built: stock counting/cycle counts, barcode scanning UI, unit-conversion-aware posting, stock reservations. See docs/inventory-engine.md "What's deferred".
- **Phase 4 — Procurement**: suppliers, purchase orders (draft -> submit -> approve -> receive/cancel), goods receipts (partial-receipt aware, posts through the inventory engine), purchase returns. Not built: Purchase Requests/RFQ stages, amount-threshold approval workflow (deferred to Phase 7's workflow engine), supplier-specific pricing. See docs/purchasing.md "Not yet implemented".
- **Phase 5 — Sales**: customers, sales orders (draft -> confirm/reserve -> dispatch -> cancel, with partial dispatch), stock reservation (row-locked the same way as the inventory engine's on-hand movements), sales returns. Not built: quotations, customer-specific pricing, credit-limit enforcement, backorders, and distinct picking/packing stages (dispatch is currently the single fulfillment step). See docs/sales.md "Not yet implemented".
- **Phase 6 — Reporting**: dashboard summary, low-stock and stock-valuation inventory reports, sales-by-product/customer and purchases-by-supplier (computed from actual dispatches/receipts, not ordered quantities), warehouse activity, CSV export on every report endpoint. Read-only phase — no new tables, no new stock-mutating code. Not built: Excel/PDF export, role-specific dashboards, dead/slow/fast-moving stock analysis, forecasting. See docs/reports.md "Not yet implemented".
- **Phase 7 — Configuration**: entity-agnostic custom fields (with server-side validation against their definitions), a tax engine (categories/rates, currency-agnostic), a pricing engine (customer/warehouse/general price lists with precedence resolution), in-app notifications (not yet wired to email/SMS/push — no provider credentials exist), and a configurable amount-threshold approval workflow for purchase orders. Not built: custom forms as a designed layout, quantity-break/promotional pricing, composite taxes, multi-level/escalating approval chains, a background job scheduler to trigger notifications automatically. See docs/configuration.md, docs/workflows.md, docs/notifications.md.
- **Phase 8 — Mobile/Offline**: stock counting (create/snapshot -> start -> submit -> approve, posting variance through the inventory engine), barcode lookup, an idempotency mechanism applied to the write endpoints a mobile client would retry, and the Flutter offline architecture (Drift-backed sync queue + replay service, camera barcode scanning on Android/iOS with a text-field fallback elsewhere). Flutter's platform scaffolding (`flutter create .`) was generated and `flutter analyze`/`flutter test`/`flutter build web --release` all verified passing — two real bugs were caught and fixed this way (see docs/testing.md). Not built: any screen that actually queues into the offline sync queue, automatic sync-on-reconnect, and a conflict-resolution UI. See docs/mobile-offline.md "Not yet implemented".
- **Phase 9 — Advanced** (AI assistant explicitly excluded per user request): POS (registers/sessions/immediate sale/void, reusing the inventory engine), demand forecasting (average-daily-usage reorder suggestions — never auto-orders), outbound webhooks (HMAC-signed, synchronous best-effort delivery — no retry queue exists yet), integration connection storage (abstraction only, no real connector), and subscription/plan record-keeping (no payment gateway, no enforcement). AI assistant architecture (master spec §31) was **not built** — skipped by explicit instruction, not an oversight. See docs/pos.md, docs/forecasting.md, docs/integrations.md, docs/subscriptions.md for what's deferred within each.

## Final status

All phases from the original plan are now implemented except the AI assistant architecture (skipped by request). The platform is a working, tested, multi-tenant inventory ERP core with procurement, sales, reporting, configuration, mobile/offline support, and POS — see each phase's docs above for exactly what's real versus deferred within it. Nothing in this repository claims completeness it doesn't have: every doc's "Not yet implemented" section is accurate as of the last commit touching that area.

## Hardening pass (post-Phase-9)

A follow-up pass closed gaps identified after Phase 9:

- **Admin panel completeness** — every backend module now has a Flutter screen (see docs/flutter.md "Screen Coverage"); Windows/Android/Web builds were all actually run and verified in this environment (not just documented), and the `ios/` project was scaffolded (never built — no Mac available).
- **Backend**: added missing update/delete endpoints for tax categories/rates, price lists/items, and workflow rules; enriched purchase/sales order line-item responses with the product's SKU/name (previously the client only had a raw product UUID to show); added `GET /auth/me/permissions` for client-side permission-aware UI.
- **Flutter**: Purchase/Sales Order detail screens now hide approve/receive/dispatch/cancel actions the current user doesn't have permission for; Suppliers/Customers/Warehouses gained edit; Settings screens gained delete where the backend supports it; reports gained a "copy as CSV" action.
- Explicitly **not** done in this pass (still open): Excel/PDF export, a background job runner, real external integrations, multi-level approval chains, CI/CD, backup/restore automation — all previously identified and intentionally out of scope (infra/ops was explicitly excluded from this pass; the rest remain lower-priority polish on an already-complete read/write surface).
